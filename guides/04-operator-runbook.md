# Регламент оператора — обслуживание парка офисов

> Гайд В4. Внутренний документ (НЕ для клиента). Как мы выпускаем обновления, откатываем,
> реагируем на сбои. Связано: office-boilerplate/{update.sh, rollback.sh, ENGINE_VERSION},
> [[openclaw-deploy-progress]].

## Модель: мы — фильтр

Клиент ничего не обновляет сам. Поток: новое → **проверяем у себя** → метим версией → льём на GitHub →
таймер у клиента (раз в неделю, ночь пн) сам подтягивает. Между нашими релизами серверы клиентов не трогаются.

Железное правило: **на GitHub попадает только то, что мы проверили.** Автообновление разносит и хорошее,
и сломанное — дисциплина на нашей стороне, не на клиентской.

## Выпустить обновление навыков (частый случай)

1. Правим болванку в `office-boilerplate/workspace/` (навыки помечены `.ours` — не снимать метку).
2. Проверяем у себя (боевой прогон или локальный тест office-sync).
3. Поднять номер в `VERSION`, закоммитить.
4. Пометить релиз: `git tag vX.Y.Z && git push --tags && git push`.
5. Клиенты подхватят ночью. Проверить у одного (лог `~/.openclaw/office-update.log`).

## Обновить движок OpenClaw у клиентов (редкий, осторожный случай)

Движок пиннится через `ENGINE_VERSION` — клиент НЕ тянет свежак от автора вслепую.
1. Ставим новую версию движка у себя, гоняем офис — всё ли живо.
2. Только после проверки вписываем номер версии в `ENGINE_VERSION`, коммит + тег + push.
3. `update.sh` у клиента увидит расхождение и обновит движок строго на эту версию.
Пусто в `ENGINE_VERSION` = движок заморожен на версии установки (безопасный дефолт).

## Откат (обновление сломало клиента)

На сервере клиента (по SSH или под нашу диктовку в Console):
```
cd /root/office-src && bash rollback.sh --list      # показать версии
cd /root/office-src && bash rollback.sh vX.Y.Z      # откатить на рабочую
```
Память клиента при откате не трогается. ВАЖНО: после отката сборка в detached HEAD — автообновление
приостановлено (клиент получит Telegram-алерт). Когда починим — вернуть на ветку:
`cd /root/office-src && git checkout master && bash update.sh`.

## Сигнал «бот лёг» или «обновление застряло»

Алерты приходят от самого офиса (update.sh шлёт владельцу в Телеграм) и от пульса.
Диагностика на сервере клиента:
```
systemctl --user status openclaw-gateway        # жив ли шлюз
tail -50 ~/.openclaw/office-update.log           # что было при обновлении
openclaw --version                               # версия движка
```
Частые причины: кончился баланс OpenRouter (клиент пополняет), git pull застрял (detached/грязь — см. откат),
сервер перегружен (тяжёлая модель на 2 ГБ).

## Пульс (мониторинг «жив»)

Крючок готов, выключен по умолчанию. Включить:
1. Завести бесплатный аккаунт **healthchecks.io**, создать check, взять его ping-URL.
2. На сервере клиента вписать URL в `~/.openclaw/.office-env`: `HEARTBEAT_URL="https://hc-ping.com/..."`.
3. `heartbeat.sh` (таймер 15 мин) начнёт пинговать, пока шлюз active. Не пинганул вовремя → алерт нам.

## Добавить клиенту персональный навык

1. Кладём навык в `office-boilerplate/workspace/skills/<имя>/` **с файлом `.ours`** внутри.
2. Тест → VERSION → тег → push. Клиент подхватит ночью (или запускаем `update.sh` вручную по SSH).
Навыки, созданные ботом/клиентом (без `.ours`), обновление не трогает.
